## Hallazgos funcionales estáticos

**INT-FOR01 P2 — release retorna payload incompatible y omite intención de publicación.** `contracts/constants/forge-release.constant.ts:8–16` admite notesFile,target,prerelease,draft; `services/forge-release.ts:98–115` sólo usa tag/notes, sin trasladar las demás opciones. Un caller que pide draft/prerelease no obtiene esa configuración. El éxito `78–87` contiene id,name, rechazados por output strict `forge-release.constant.ts:24–35` (title opcional, id/name ausentes). Specs service66/tool81 esperan id/name, schema19 prueba otro payload. Corrección derivar input/output de contrato único y comprobar todo resultado contra schema, sin publicar. No ensayo nuevo.

**INT-FOR02 P2 — defaultTimeoutMs persistente se acepta pero no llega al runner.** Entry `index.ts:29–48` añade defaultTimeoutMs/timeoutMs a objeto options, interfaces builders sólo namespace/root/exec y servicios no usan ese valor. Las spread conditions eluden excess-property check de TS. Fijar timeout1 o120000 no modifica llamada IRunExternalToolInput. Spec plugin-options sólo registra IDs. Corrección pasar wrapper forgeExec configurado o transportar opción explícita a todas llamadas.

**INT-FOR03 P2 — search ignora filtros/page/kind declarados.** `forge-search.constant.ts:18–23` acepta path/page/kind; `IForgeSearchCodeOptions` los omite y `services/forge-search.ts:49–64,122–149` no los consulta; GitLab page hardcoded1, siempre code. Caller page2 repite1, path no restringe, kind issues devuelve búsqueda código. No estado incompleto, parse inválido se convierte[] éxito. Rechazar campos no implementados o implementarlos y verificar fixture CLI real.

**INT-FOR04 P2 — finalize no se alimenta del reader normal del propio plugin.** `release-finalize/index.ts:63–67` requiere pr.headSha/mergeCommitSha; `services/forge.ts:610,285–334` no solicita/copia esos campos; schema PR detail tampoco los permite. Siempre falla por SHAs cuando se usa adapter basado en showPullRequest; tests sólo reader fake con campos manuales. Se necesita adapter release explícito con metadata y branch base verificable (hoy fallback target oculta base ausente).

**INT-FOR05 P2 — transaction step toma rechazo de negocio por ejecución exitosa.** `transactions/forge-write.ts:68,86,104` sólo lanza si isError=true. Servicios confirm-required/CLI failure se empaquetan vía toolJsonBounded (`tools/forge-write.tool.ts:42–76`); helper core `tool-response.ts:390` retorna toolJson sin levantar business ok:false. Un step retornará normal ante rechazo confirm y puede marcarse completado por caller. capabilityGrant de input ni se consulta ni se adjunta al step. Estado core del motor no inspeccionado aquí; conclusión limitada al retorno normal de step.run.

**INT-FOR06 P2 — JSON de error CLI se normaliza como éxito vacío.** `services/forge.ts:522–537` tolera run.ok=false si payload empieza {/[; lista/show luego mapea cualquier objeto, array esperado ausente=>[] o detalle con campos vacíos. Error CLI con JSON puede dar ok:true sin datos en vez de error. Comentarios prefijos no JSONlike dan fallo aunque parser soporta sliceJson, política inconsistente. Debe separar exit status del payload y validar contrato endpoint.
