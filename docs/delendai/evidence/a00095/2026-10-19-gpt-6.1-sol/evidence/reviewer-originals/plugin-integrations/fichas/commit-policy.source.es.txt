## CP-01 — P2 provisional: un error de refresh elimina las protecciones remotas previamente conocidas

En `createBranchProtectionAdapter`, `refresh()` comienza poniendo `remoteBranches = new Set()` y llama `applyEffectiveBranches()`, que muta `options.policy.protectedBranches` con la unión local + remota. Si falla la resolución del remote o la consulta al forge, retorna estado `error` después de haber borrado las ramas remotas anteriores. El scheduler y `runPushDriver` leen esa misma política; no exigen que el resultado del refresh esté `fresh`.

**Reproducción local:** `evidence/commit-policy/repro-refresh-failure.ts` ejecuta refresh correcto con rama sintética `maintenance`, luego fallo de autenticación/red, y finalmente `runPushDriver` para `maintenance`. Resultado: estado inicial `fresh` y protegida; segundo estado `error` con lista efectiva vacía; el runner observa `git push origin HEAD:maintenance`. Solo se inyectan datos y un runner; no hubo red, credenciales ni escritura remota.

**Impacto calibrado:** el control preventivo local intenta una rama que el último snapshot remoto declaró protegida. La respuesta del forge puede aún rechazar el push; no afirmo bypass de una protección aplicada por GitHub/GitLab ni modificación real de la rama. La salida estructurada señala `error`, pero la ruta normal de push no consulta esa frescura. P2 porque se pierde una defensa configurada tras un fallo transitorio y las siguientes acciones automáticas/manuales intentan el destino de todos modos.

**Corrección sugerida:** reemplazar la caché remota solo después de una respuesta válida; en error conservar el último conjunto con estado `stale`, o hacer que el driver rechace targets que dependan de una caché remota expirada. Regresión: refresh correcto → refresh fallido → push al branch antes protegido debe seguir siendo rechazado localmente o quedar bloqueado por estado stale.

## CP-02 — P2 confirmado: el parser de porcelain conserva comillas y falla con nombres que tienen espacios

`gitDirtyFilePaths` llama a `git status --porcelain=v1`, elimina el prefijo XY, pero no desescapa las rutas que Git escribe entre comillas cuando contienen espacios u otros caracteres especiales. `threshold-tracker` e `interval-timer` propagan ese literal al driver, que lo pasa como argumento de pathspec a `git add`.

**Reproducción con Git real:** `evidence/commit-policy/repro-porcelain-quoted-path.ts` inicializa un repositorio temporal, crea `a b.txt`, obtiene `?? "a b.txt"`, y observa que el helper devuelve `"a b.txt"` (con comillas literales). `git add -- "a b.txt"` falla con `pathspec '"a b.txt"' did not match any files`. Resultado en `evidence/commit-policy/repro-porcelain-quoted-path.log`; el checkout auditado no se modificó.

**Impacto calibrado:** el trigger por threshold/interval no puede confirmar estos archivos por su ruta. No se prueba pérdida del contenido ni afecta a paths no citados. La corrección debe preferir `--porcelain=v1 -z` con parseo NUL, incluido el formato de rename, o implementar el decoder de quoting de Git; añadir cobertura de espacios y otros caracteres especiales.

## Observación: propositor de tormentas degradado en producción

La ruta pública de `register()` llama a `fileRepairProposals` sin `proposalStore`. `IMcpPluginContext` tampoco contiene ese puerto. Por contrato el proposer devuelve `proposed: false` con `NO_PROPOSAL_STORE_REASON` y no crea ni sincroniza la propuesta; el spec fija ese comportamiento. Es una función incompleta reconocida explícitamente en comentarios de `index.ts` y la prueba del cambio x00535, no la presento como defecto inesperado ni como creación efectiva de propuestas. La exposición y el logging de tormentas sí existen. Pendiente contrastar documentación/roadmap antes de decidir si se registra como hallazgo de producto.

## CP-03 — P2 provisional: el registro omite workspaceRoot y deja el índice compartido sin exclusión

En `index.ts`, el objeto `sharedDriver` omite `workspaceRoot: ctx.workspace.root`, aunque sí pasa `pluginCacheDir`. El engine reusa ese objeto y `withGitWriteLock` no toma mutex cuando `workspaceRoot` es `undefined`. Luego `commitWithGuard` también elige el camino de índice compartido por su guard inicial (`workspaceRoot === undefined || branch === undefined`); el camino aislado con `GIT_INDEX_FILE` y mutex `.git/index` solo se usa cuando se suministra la raíz.

Los unit tests de índice aislado pasan la raíz manualmente y verifican el camino que funciona; los tests de register no comprueban la inyección. La reproducción `repro-register-missing-workspace-lock.ts` intercaló dos drivers con scopes disjuntos y raíz omitida: los dos hallaron la ruta del otro en el índice, respondieron `CROSS_AGENT_CONTAMINATION` y el índice simulado quedó limpio. Es una intercalación de un runner falso, no dos procesos reales; confirma el orden y resultado del algoritmo, pero no bytes perdidos en el worktree. La evidencia de código sí confirma que la producción omite el mutex interproceso y el índice aislado. Impacto: interferencia/fallo de commits concurrentes y reset del staging compartido; no afirmo pérdida de contenido. Se necesita regresión con dos procesos contra un repositorio temporal.

## CP-04 — P2 provisional: el checkpoint WIP no verifica el propietario de la slice

Cada servidor construye `workRefAgent` con su identidad local y pasa una función `agentDeclared`, pero la entrada `IEngineEvent` de slice solo lleva proposalId, sliceId, paths y eventId. La ruta WIP se ejecuta antes de la resolución de ownership; `createPolicyPersistence` solo rechaza identidades no declaradas y no consulta el lock que identifica quién posee la tarea. Por tanto, dos instancias declaradas pueden atribuir el mismo checkpoint a sus propios agentes.

**Reproducción:** `evidence/commit-policy/repro-wip-slice-owner-mismatch.ts` usa un repo temporal y `bindWipCheckpointPort` real. Dos instancias con `agent-a` y `agent-b` reciben el mismo `f00999/S1`, eventId y scope, y crean refs distintas bajo `refs/heads/wip/`. Se desactivó solo el auto-push del fixture para permanecer offline. No se ejecutaron dos servidores MCP ni se abrieron PRs; está probado que el port acepta y crea refs para el mismo claim bajo ambas identidades. La propagación desde listeners concurrentes se deduce del registro/código. Remedio: adjuntar propietario/task del claim y verificar contra el registro autoritativo, o adquirir idempotencia exclusiva por evento antes del checkpoint.

## CP-05 — P2 confirmado: el modo co-authored-by puede borrar el header y trailers del commit

`stripTrailers()` elimina hacia atrás cualquier línea final con forma `Clave: valor`, incluyendo `fix: asunto` (el propio header Conventional Commit), `Signed-off-by` y `Reviewed-by`. `appendAuditTrailer()` añade después solamente su nuevo trailer. La reproducción `evidence/commit-policy/repro-coauthor-trailer-header.ts` pasa un mensaje convencional con dos trailers y produce únicamente `Co-authored-by`; todos los campos originales desaparecen. Es una función pura, sin Git.

Impacto limitado a `audit.trailer="co-authored-by"`, configuración explícita porque el default es `none`: puede dejar commits sin asunto y quitar texto/firma aportados por el autor. P2. Corrección sugerida: reconocer únicamente trailers emitidos por el plugin y preservar header, cuerpo y otros trailers Git; añadir pruebas de re-ejecución idempotente.

## CP-06 — P2 confirmado: no se registra la tool status que prometen docs y knowledge

`README.md`, `README.es.md` y el bloque `knowledge` prometen `commit_policy_status`; `status-tool.ts` tiene builder y tests, pero `index.ts` no lo importa ni lo añade al array de `tools`. El modelo recibe instrucciones para llamar una herramienta que el host no expone. El registro sí añade branch-protection, commit, push, run, storms y settlement, más work-ref (siete); ambas READMEs enumeran cinco e incluyen el status ausente. README inglés/español dicen identity default `global` aunque el schema usa `repo`; README español y knowledge dicen trailer `co-authored-by` aunque el default es `none`; README español dice que cadence solo corre por tool manual aunque slice/interval arrancan timers. P2 por capability ausente y contrato operativo contradictorio. Registrar status, sincronizar docs y añadir test de conjunto de tools/defaults.

## CP-07 — P2 confirmado: el threshold ve una carpeta untracked como un solo fichero

`gitDirtyFileCount` y `gitDirtyFilePaths` usan porcelain sin `--untracked-files=all` / `-z`. Git resume doce ficheros nuevos de una carpeta como `?? new-dir/`; el threshold cuenta `paths.length` y ve uno. La reproducción usa los helpers de producción en un repo temporal y da policyCount=1 frente a 12 entradas expandidas. Un threshold de diez no dispara con esos doce ficheros; interval transporta una ruta de directorio. P2, sin afirmar pérdida de contenido. Usar estado NUL con untracked expandidos y cubrir dirs/espacios/renames.

## CP-08 — P2 confirmado: el presupuesto de tools/list está muy por debajo de la huella medida

El manifiesto declara staticBytes=4.200, hard=5.200 y source token-budget-real. El tipo de core define staticBytes como bytes de tools/list y hard como techo absoluto. La medición del registro real usando MCP in-memory obtiene 7 tools, 9.338 bytes de definitions, 3.717 bytes de output schemas y 9.356 bytes del envelope completo. Son bytes UTF-8 serializados, no tokens. La medición usa un workspace git temporal y no ejecuta tools ni red. Status sigue ausente; añadirlo crecería la superficie. P2 por superar el hard cap declarado y afectar la selección de plugins. Actualizar medición/caps o reducir y cargar herramientas de forma lazy; agregar gate de drift. typicalOutput y adaptiveActivation no se midieron.
