# error-reporting — ficha independiente completa

Auditor: `gpt-6.1-sol` (Codex). Snapshot: `514758e783620c8953079be4d71fceccacb3de8b`.

## Opinión y nota

**4/10.** La tubería está bien dividida, es asíncrona y protege la llamada original; el destino está fijado, el DTO se limita y la persistencia incluye deduplicación, límites, reintentos y cortacircuito. Sin embargo, la frontera principal de privacidad se puede falsear con un resultado MCP controlado por el proyecto: el sufijo `node_modules/@delendai/<nombre>` se toma como procedencia propia sin comprobar catálogo confiable. También hay contradicción material entre README/knowledge y el valor efectivo de `enabled`, y el mapa de permisos no representa las dos herramientas. Los controles locales son amplios, pero esos defectos pesan más que la cobertura declarada.

## Qué hace realmente

El plugin observa resultados de herramientas y fallos de ciclo de vida. Detecta fallos, evalúa procedencia, normaliza frames, crea un DTO seguro, aplica redacción y valida el objeto y su JSON. Registra intentos, consulta la política de dedupe/límite diario/backoff/circuit breaker y reclama el despacho antes de usar el reporter. El reporter hace una comprobación acotada de conectividad a `api.github.com`, y luego ejecuta `gh issue create` hacia el repositorio de DelendAI mediante el runner compartido. Fallos del proceso se guardan para reintento sin propagarse a la llamada observada.

Registra dos herramientas: `report_status`, lectura local de estado, y `diagnose_log`, diagnóstico local de un log que solo trata de abrir una issue si la entrada contiene `openIssue.confirm: true` y un `shapeId` concreto. El plugin está activado y `enabled` resuelve a `true` por defecto. Aunque el aviso por inicio informa de ese estado y de la opción para deshabilitarlo, README y knowledge generada afirman lo contrario.

## Hallazgos confirmados

### ER-01 — P1: frame MCP falsificado suplanta paquete propio y filtra identidad del proyecto

`frame-extractor.helper.ts` acepta cualquier frame que incluya `node_modules/@delendai/` y conserva el nombre que sigue, sin comprobar si pertenece a DelendAI. `internal-classifier.helper.ts` considera propio ese frame. `report-builder.helper.ts` admite un error obtenido del resultado estructurado MCP. Una reproducción con `@delendai/acme-billing-private` pasa por `extractObservedFailure`, `asReportableError`, `buildSafeReport` y `validateSafeReport`: se clasifica como interno, el DTO contiene ese `packageId` y frame, y el validador responde ok. La salida está guardada en `evidence/error-reporting/repro-project-stack-spoof.log`; la ejecución no contactó la red.

En operación, si hay conectividad y `gh` autenticado, la identidad privada del paquete/proyecto podría enviarse en la issue automática. No se observó envío de ruta absoluta o mensaje raw. La recomendación es derivar pertenencia de identidad registrada/confiable y rechazar sufijos que no estén en la lista de paquetes first-party. Confianza alta: reproducción con transformadores y validador usados en producción.

### ER-02 — P2: la expectativa de consentimiento difiere del runtime

La opción ausente acaba en `enabled: true`; el manifest dice “on by default”, `startupActivation` también es true y el aviso comunica reportes automáticos. README y tabla de configuración dicen desactivado por defecto y requieren `true`; el texto de knowledge para modelos repite desactivado/opt-in. Esto puede hacer que un usuario que copie la configuración según esos documentos espere que nunca se envíen informes. El aviso interactivo reduce la sorpresa, pero no corrige documentos ni hosts desatendidos. No se envió ninguna issue en la auditoría. Alinear todos los contratos con el valor runtime o cambiar el default de manera coordinada.

### ER-03 — P2: el mapa de permisos tiene herramienta omitida y capacidades sobrantes

El manifest comenta que solo existe `report_status`, aunque se registran `report_status` y `diagnose_log`. Asigna a status `network`/`forge-write` pese a que solo lee estado local, y omite filesystem-read. `diagnose_log` puede enviar issue explícitamente confirmada, pero al no tener entrada individual hereda todos los permisos globales, incluso filesystem-write. El core utiliza la asignación específica cuando hay match y hace fallback al set global cuando no lo hay. No encontré bypass del runtime; la discrepancia afecta least privilege y hosts que consumen esos metadatos. Mapear ambas herramientas a sus efectos mínimos reales.

### D114 — discrepancia previa confirmada

`claimDispatch` devuelve `false` cuando la tienda es de estado no confiable y también cuando hay una reclamación activa; el llamador cuenta ambos como `deduplicated`. La suite reconoce esos dos bloqueos pero el caller elimina su semántica al convertirlos a un booleano. Confirmo el hallazgo existente; no lo duplico en el índice raíz. Exponer resultado discriminado y contar el estado no confiable como almacenamiento/reporting no disponible, no dedupe.

## Calidad, tests y token

Se revisaron los módulos fuente de registro, opciones, análisis de origen, extracción y clasificación de frames, transformación de reportes, validadores, firma, ejemplo sintético, runner/reporting, store, scheduler, claims en vuelo, contadores, tools de estado/diagnóstico, intake del log y disposal; además de package, manifest, README, knowledge y pruebas del plugin. Tests útiles cubren privacidad adversarial, registros corruptos, carrera de claims, lifecycle/dispose, scheduler y reconciliation del funnel. No existía caso contra el sufijo `node_modules/@delendai/<proyecto>` que se reprodujo fuera de suite.

Resultado registrado: 25 archivos, 161 tests aprobados. Vite emitió aviso de configuración por import extensionless que puede dejar de soportarse. La suite usa fixtures/mocks; no prueba autenticación real, la escritura remota, host MCP real ni permisos efectivos del host. La reproducción ER-01 solo pasó la ruta local de transformación y validación.

El manifest declara 3.500 bytes estáticos, 600 adaptativos, salida típica de 900, hard cap 4.200 y warning 3.800; fecha de medida declarada 2026-08-25. Son valores declarados, no medición de tokenizer repetida ahora. Status presenta salida compacta y diagnose mantiene esquema MCP de salida compacto. No hay comparación E2E native/managed/adaptive ni coste por tarea. No se observa cargo de tokens por el envío con CLI local; el costo de red/servicio no fue medido.

## Límites de esta opinión

El snapshot evaluado es el indicado arriba. No se hicieron peticiones GitHub ni se usaron credenciales, no se probaron cuotas ni se simuló una instalación externa completa. La activación real del envío es inferida del wiring del reporter y del runner, condicionada a conectividad y auth de `gh`; no es una escritura externa observada. Los contadores token son los del manifest y no costes E2E medidos.
