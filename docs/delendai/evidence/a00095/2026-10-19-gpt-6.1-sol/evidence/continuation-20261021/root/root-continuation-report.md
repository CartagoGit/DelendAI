## Public orphan reclamation, owned repositories only

The entire `tools/scripts/reclaim/reclaim-orphans.script.ts` and the three core removal/reaper/worktree-state helpers were read. This adds two direct public-script cases beyond pure helpers. `repro-reclaim.py` creates three independent private repositories, each with a local bare remote; actual Bun runs the unmodified script with --apply only inside that fixture. No user's branch, worktree or remote is touched, and no Git object is garbage-collected.

Valid-base control retains the branch with a unique commit. An invalid --base makes rev-list fail; its empty stdout is parsed/defaulted as zero, and the public script returns0 after deleting that same unique branch. A separate valid-base race case initially has a merged branch; a local PATH wrapper interposes a real competing Git update-ref immediately before the script's real branch-D call. The script deletes the newly advanced branch too. These are deterministic interleavings, not a statistical stress test. Bun/real Git/subprocess effects are real inside owned fixtures; the interposition is an explicit test seam.

Raw output's `uniqueTipReachableFromDevelop` label is misleading: its value is actually the output of `git rev-list --count develop..<uniqueTip>`, namely one commit **outside** develop. Keep the original logs/script untouched; `reclaim-result-clarified.json` supplies the corrected property name. Neither branch-removal result asserts the commit bytes are immediately irrecoverable: the captured hashes/objects remain in the temporary object store. The demonstrated failure is removing the only branch reference despite the lossless-cleanup promise.

`unit-removal.service.ts` also issues local update-ref -d without an expected old SHA; its remote drop uses force-with-lease with a captured tip, which is a positive protection and must not be described as absent. The core local-unit path was traced statically, not executed in these non-unit branch fixtures. `inspectWorktree` collapses failed status to empty paths, but Git removal without --force can still refuse dirty edits; do not promote that helper alone to a proved destructive bypass.
