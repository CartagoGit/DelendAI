Snapshot: `031f6396a78bfcceadf87598a462c9a8164a86dd`. The seven proposal documents were read completely. Supporting product/test ranges, hashes and fixed SHA are in `review-proposals-coverage.json`. This is a semantic criterion review, not acceptance of the proposals or changes to their declared states. Tests below were **read, not executed**. G131/G132 and earlier judgments retain their own snapshot and scope.

## f00765 — Personal accounts outside the repository

**Current implementation: substantially present; one explicit criterion is inconsistent.** `personal-layer.service.ts:83–92` derives the personal path under the user's config root; `:98–120` validates missing/malformed files; `:142–179` replaces whole accounts by accountId and overlays provider bindings. `cli/assemble.ts:304–312` actually loads and merges it; `:1465–1471` exposes layer/path diagnostics. The tests cover SSH/HTTPS clone identity, no remote, missing/bad file and whole replacement without profile leakage (`personal-layer.service.spec.ts:45–85,89–135`); layer-origin diagnostics are asserted in `load-config-file.spec.ts:321–359`.

**Inconsistency:** proposal acceptance `f00765:41` explicitly selects the **integration remote**. Product `personal-layer.service.ts:61–69` selects origin or the first remote and never reads the integration branch's configured remote. A fork with origin and upstream integration can therefore use a different personal project key than the stated contract. The inspected identity specs only create origin, so they do not cover that criterion.

Migration is implemented: `personal-accounts.migrator.ts:61–63,118–146` moves login-bearing accounts and their provider bindings through the personal writer before editing shared config. `:159–170` holds the target mutex; personal and shared files are **two separate atomic writes**, not a two-file transaction. Idempotence follows from detecting remaining personal accounts (`:151`), but framework startup/journal orchestration was not fully read in this follow-up. No actual move or `--check` invocation was performed. Pending: integration-remote regression, migration framework/journal chain and cross-person/clone behavior beyond these fixtures.

## f00766 — Shared discovery and usable-account verdicts

**Current implementation: shared catalogue/PATH probe confirmed; universal verdict parity is incomplete.** `known-clients.constant.ts:22–148` lists the combined clients including OpenCode. Both runner `healthcheck/probe.ts:14–31` and selector `discovery/real-deps.ts:19–24` use core probeClientCommand. Core `client-discovery.service.ts:62–100` maps status text to verdict/evidence, `:155–198` runs login checks only when requested, and `:206–247` lists host models without opening a client config. Inspected recorded-answer tests cover needs-login/needs-plan/quota-exhausted/unknown, OpenCode credentials and login consent (`client-discovery.service.spec.ts:22–127`), plus listing (`:189–220`).

**Inconsistency with “same report everywhere”:** selector's real adapter returns only `.installed` (`real-deps.ts:20–22`); discoverRankedProviders consumes roster.available, not the richer client verdict (`services/discover-ranked-providers.service.ts:28–48`). Runner's public discover route checks consent then calls PATH-only discoverProviders (`tools/discover.tool.ts:60–85`; `bootstrap.ts:85–110`); it adds model lists, but not probeLogin verdicts there. probeLogin exists separately (`bootstrap.ts:156–175`). Sharing catalogue and low-level probe is not one uniform usable-account discovery report.

The “unknown, never guess” criterion also needs tightening: any zero-exit login command with no stopper becomes usable (`client-discovery.service.ts:97–100`), and Aider's configured login-status command is merely `--version` (`known-clients.constant.ts:105–117`). This source does not prove it can run paid work. No real-machine verdict or account reachability was tested. Pending: unified caller verdict propagation and real-client recorded-answer completeness; full consent persistence and bootstrap path were not re-audited here.

## f00767 — Observed quota and declared request budgets

**Current implementation: key writer/budget/journal criteria confirmed statically; real unattended end-to-end acceptance remains untested.** `quota.ts:189–195` preserves existing groups in provider snapshots; `:203–233` records per-group windows under its mutex, keeping other windows/groups. `quota-sink.service.ts:24–40` maps provider→account groups; actual composition wires it in `index.ts:200–204`, and build-manager passes it to createApiInvoker (`build-manager.ts:212–217`). The sink is fire-and-forget and catches write errors: no immediate durability guarantee follows from returning the API result.

`quota-reservation.service.ts:102–135` combines fresh observations with declared rolling request budgets, counting reservation history; `:177–260` checks/records holds under the ledger mutex; `:283–297` preserves history when releasing. Missing groups and unknown quota are refused (`:329–340`; `:146–160`). Running journal entries contain remaining/source information (`manager.ts:267–273`; `reserveQuota:222–234`). Specs explicitly test group preservation/mapping (`quota.spec.ts:214–299`) and budget spending/window release/stale observations/old ledger (`quota-reservation.service.spec.ts:248–329`).

Limits: this follow-up did not read the complete API response/429 producer or execute a real request, so source sink wiring plus a unit helper's 429 expectation is not proof of every vendor response path. A mutex in the reservation ledger is not a global transaction joining observations, quota write completion, invocation execution and journal writes. No money/token cap is inferred from request budgets. Pending: controlled public invocation through 429/header production and unattended acceptance with an explicitly authorized real account.

## f00768 — One outcome store and one ranking

**Current implementation: shared store and scoring formula exist; full shared-decision acceptance is inconsistent with composition.** `model-outcome-store.service.ts:33–56` reads legacy success lines, and `:60–108` stores redacted appended lines under a mutex. Selector calibration reads/writes this store (`calibrate/store.ts:15–45`). Migration declares epoch 5→6 and a conflict-preserving move (`model-outcomes.migration.ts:16–37`). Runner actual composition supplies the store append (`index.ts:197–199`); hop completion writes unknown, failure failed (`manager.ts:299–320`), correctly avoiding an automatic success→accepted conversion. The record contains invocation/provider/account/taskMode/latency here; no result tokens/cost/retry values are passed to this append even when the successful result contains usage (`:309–312`).

Core ranking folds judged outcomes by task kind (`model-ranking.service.ts:42–71`), scores capabilities/mode/dial/evidence (`:74–130`) and honors an available pin (`:137–176`). Inspected specs cover evidence changes, unavailable reasons and pins (`model-ranking.service.spec.ts:45–113`). Self-learning computes per-kind judged rates, sample counts and optional cost text (`model-lessons.helper.ts:32–115`).

**Inconsistency:** runner `router/score.ts:46–50` supplies capabilities/mode/dial but no outcome evidence; selector `rank-providers.ts:57–64` supplies an empty task and available=true, with optional calibration. Core ranking takes no account quota or observed remaining amount. Therefore one formula does not establish the acceptance at proposal `:55,74` that every tool returns the same evidence/quota-based decision. Earlier G30 must stay nuanced: duplicate formulas are not current, but caller inputs and evidence use still differ. Self-learning sums only costed accepted results and keeps one unit (`model-lessons.helper.ts:60–67,85–88`); no claim of comparable multi-currency cost efficiency is supported. Pending: complete outcome fields/production measurement, consistent ranking inputs and an end-to-end comparison; no real hops performed.

**Current implementation: offer/filter/answer-dependent write criteria present; policy text has drifted.** `account-offers.service.ts:26–60` offers only usable discoveries with recognized login, skips declared/vendor-mode/declined accounts and defaults automation=false. `account-offer-flow.service.ts:55–87` asks and makes one addition for answered yes/no entries; undefined answers cause no write. CLI lists without terminal/--yes (`accounts.command.ts:37–64`); init service returns before discovery without a terminal (`init-accounts-offer.service.ts:21–25`). The inspected specs cover yes/no remembering, unanswered no-write, mode and malformed/schema-invalid writer refusals (`account-offers.service.spec.ts:48–158`; `personal-layer-writer.service.spec.ts:24–77`).

**Document drift:** the proposal goal/non-goals say automation stays off and enabling it is a later personal step (`f00775:25,47`). Current product asks a separate explicit automation question and supports --yes --allow-automation (`accounts.command.ts:37–63`; `account-offer-flow.service.ts:74–79`); tests expect opt-in true (`account-offers.service.spec.ts:169–195`). This is explicit user choice, not unsolicited automation; update acceptance or justify the deliberate scope extension. The separate setAccountAutomation path is not literally the same addition writer; it also writes under mutex (`personal-layer-writer.service.ts:125–170`). No account offer or actual personal configuration was touched. Pending: terminal interaction and full successful-init caller/registry tests beyond the helper, existing-directory permissions, plus f00765's project identity discrepancy.
