## Plugin card

**Purpose and implementation.** This stable-declared plugin is a working local observability layer: it records invocation attribution, provider-reported token metadata, explicit baseline comparisons, response volume, outcomes and optional delegation measurements. It produces on-demand reports, periodic summaries, local session hygiene and checkpoint advisories. It is useful without a model provider because ordinary calls still have plugin/tool, timing and byte information; model/usage/cost are explicitly unknown when no structured provider measurement exists. It is neither a provider quota meter nor an invoice ledger. Subscription prices remain null. Stable maturity overstates the correctness of some derived diagnostic and savings metrics.

**Public MCP contract.** Actual registration exposes three tools: report, confirmed history clear, and session hygiene (`src/lib/tools/index.ts:25-48`). Report supports filters, five grouping axes, capped bucket limit200 and normal/compact/full detail. Compact suppresses expensive-call lists, result-size rankings and plugin breakdowns while keeping totals and buckets. The clear tool declares destructive/write effects and host-state root and requires explicit confirm:true. It returns absolute internal paths on success (`clear.tool.ts:59-61`), contrary to the local generated hint; this was statically observed, not executed on user history. Report/hygiene use a compact generic output schema, so successful schema acceptance does not validate each detailed metric. Raw standalone clear-builder confirm:false is rejected by the installed SDK's success-only output schema; the normal core host normalizes error structured content, so the isolated SDK rejection is not evidence of normal host breakage.

**Dependencies and authority.** Runtime needs core helpers, shared contracts, MCP SDK and Zod; no other plugin package dependency. Client identity comes from hostIdentity, not provider environment sniffing. Attribution resolves the longest loaded peer prefix; routed capability responses are attributed to the reached tool. Provider/model tokens are extracted only from typed numeric metadata and explicit baseline options; no extra LLM request calculates savings. Core already supplies an invocation-local elapsedMs, but this plugin instead reconstructs timing through a FIFO by tool name (USAGE-02). Legacy and enriched summary paths coexist; both use the same raw record model and preserve degradation appends under a summary mutex. Consolidating those writer paths would reduce duplicate-maintenance risk.

**Effects, isolation and lifecycle.** Declared permissions include filesystem read/write and network. Files are host state under the results namespace, not disposable derived cache. Boot resolves pricing, cleans only stale zero-byte tmp files, primes a summary and installs an unref'd periodic rollup timer. Pricing can fetch a public third-party JSON table on missing/stale cache with a one-second AbortController; it has no offline option. This audit blocked fetch and did not send any credentials or usage records. Metadata writes run through redaction and a file mutex; appends open/write/fsync/close, while summaries use atomic replacement. Natural beforeExit drains live buffers; SIGKILL and forced process.exit do not provide an async durability guarantee. Append failure is intentionally best effort with an incident and stderr warning; it is not retried transactionally. The summary interval has no dispose hook and is explicitly acknowledged as process-lifetime scoped in source (`index.ts:282-311`). Re-registration lifecycle effects were not executed here. Host-only lifecycle events are schema-validated and opt into MCP identity correlation by literal id equality; local session hygiene repeatedly labels its narrower observation boundary.

**Verified strengths.** The 68 passing tests cover extraction, baseline accounting, metadata-only reports, buffered append and synthetic redaction, shared flush barriers, clear/history semantics, degradation-versus-rollup races, missing/torn-tail log tolerance, independent spend windows and subscription/null pricing. The 1,000-call buffer test checks push latency below5ms and complete local drain; this is a fixture test, not an end-to-end host p99 benchmark. Unknown context-rehydration effectiveness and privacy-gate counter remain null with explanatory notes instead of invented measurements. Response ranking and compact projection give concrete ways to reduce model context. No prompt or response body is copied into ordinary records; bounded normalized error messages are intentionally retained as diagnostics.

**Confirmed defects.** USAGE-01: a valid issues collection, even empty, becomes a schema-incongruence error because a generic field name is interpreted as validation evidence. USAGE-02: reversed completion order exchanges concurrent same-tool start times; the accurate host timing parameter is ignored. USAGE-03: one row's measured25% savings turns into33% after aggregation because the denominator changes from baseline to tokens spent. These have independent source traces and deterministic local probes. Existing TOK-02 (heuristic schema bytes labeled estimated:false), D75/D83 (silent partial JSONL reads), G103 (boot pricing network) and G96 (top-level legacy zero savings versus unavailable provenance) remain related or duplicated observations, not newly counted findings. A valid JSON null row additionally passes the raw reader and crashes window filtering; this is recorded as a D75/D83 robustness extension.

**Costs measured locally.** Real MCP SDK in-memory listing with namespace `fixture`, with no plugin boot and no external transport: **3 tools; 3,116 bytes of complete definitions; 978 input-schema bytes; 499 output-schema bytes; 3,130-byte list envelope**. Individual definition sizes: report1,523; clear784; hygiene809 bytes. One synthetic ordinary invocation report yielded **5,678 bytes normal versus2,984 compact** for the serialized MCP result. These figures depend on the namespace, installed SDK1.32.1 and fixture contents. They are wire-object byte counts, not model tokenizer measurements, hosted token charges or proof that host context receives both text and structuredContent. The raw reader loads and splits the entire historical log for reports and every rollup; no log size cap, streaming aggregate or retention/compaction is implemented. Window filtering happens after reading. Session-hygiene sorting also scans whole history, and per-session live state has no eviction. Large histories and many synthetic caller session ids therefore deserve a bounded-state design and benchmark before promising cheap long-running hosts.

**Score: 6/10, provisional.** This is substantially implemented and usefully testable, with strong local durability and explicit missing-data boundaries. Its central product is trustworthy measurement, so fabricated schema errors, incorrect concurrent latency and inconsistent savings percentages materially lower the score. Heuristic activation/schema KPIs should remain visibly estimated; lack of complete record validation and unbounded historical reads limit robustness. Correct those existing seams before adding new telemetry layers. Score is based on the inspected snapshot and focused fixtures, not provider measurements or field deployment.

No production files, claims or proposals were changed. No browser, VSCode host, real provider, credentials, network request or user log deletion was involved. Remaining tests and host lifecycle/large-history behavior are honestly open. The three new defect hypotheses are demonstrated at their stated pure-function/callback boundary; they do not prove historical production frequency, provider billing impact or end-to-end user-host behavior.
