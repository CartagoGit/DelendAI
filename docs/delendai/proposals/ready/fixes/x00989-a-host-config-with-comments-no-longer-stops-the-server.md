# x00989 — A host config with comments no longer stops the server

## goal

A workspace whose `.vscode/mcp.json` carries comments must boot the delendai MCP host server, and that config must be rewritten exactly as a plain-JSON one is — same rules, same result — with the file's own comments, key order and formatting left alone. A host config delendai cannot read must be reported as one failed migration instead of taking the whole server down.

## why

Observed live in another project that consumes delendai (2026-10-28, 07:01). That workspace's `.vscode/mcp.json` is generated by its own `bun run mcp:sync` and opens with two `//` comment lines. The host-config migrator read it with `JSON.parse`, which cannot parse a comment, and the `HostConfigParseError` it raised escaped `plan()` — the engine guards `apply()` with a try/catch that records a `failed` outcome, but `plan()` is not guarded at all — and reached the boot's terminal catch, which exits 1. The editor's MCP client then restarted the server in a loop and every tool call failed with `MPC -32000`.

The premise the strictness rested on is false. The migrator's own header says that `.vscode/mcp.json` is the VS Code spec, JSON only, no comments — but VS Code parses that file as JSONC, and this repository already established the opposite for the `init` path (x00890 recorded it: editor MCP configurations are JSONC). The migration path was never updated with it, so the one path that runs on every boot of every adopted project is the one that cannot read a commented file.

The second half is the same defect seen from the other side: a file delendai does not own, in a format delendai chose, took down an editor integration that had nothing to do with it. The repository already has the answer for that shape of problem — the boot-time reconciliation refuses to start a DEGRADED workspace unless `DELENDAI_STARTUP_STRICT=1`, because a degraded workspace is exactly the situation in which an operator needs the server up to ask it what is wrong. The migration engine answered the same situation with a crash.

## non-goals

- Not changing WHAT a host config is rewritten into. The rewrite rules, the fields walked, the identity renames and the resulting content are exactly today's; a plain-JSON `.vscode/mcp.json` must come out byte-for-byte as it does now.
- Not changing `.cursor/mcp.json` or `.continue/config.json`: they are already read tolerantly, and they are left exactly as they are.
- Not changing the fail-closed behaviour of a development-policy contradiction (`push-target-contradicts-policy` and its siblings). That one is a configuration error with a stated remedy — removing `push.branch` from the offending `delendai.config.json` — and not a crash; the remedy is the owner's to apply.
- Not touching the Codex TOML path or the `mcpServers`-array shape: they are rewritten by their own rules and are not affected by comments in a JSON file.

## acceptance

- A `.vscode/mcp.json` whose only departure from JSON is a line comment is planned and applied without throwing, and the migration rewrites it exactly as the plain-JSON path does.
- A `.vscode/mcp.json` that is neither valid JSON nor valid JSONC still raises `HostConfigParseError`, and the file is left byte-identical — the existing contract, kept.
- A plain-JSON `.vscode/mcp.json` is written exactly as today: the same bytes, the same tab indentation, the same trailing newline.
- A commented `.vscode/mcp.json` that names the old identity is rewritten, and the file keeps its comments outside the rewritten member, its key order and its own formatting.
- A commented `.vscode/mcp.json` that names nothing old is not written at all — byte-identical before and after.
- `plan()` is guarded by the same failure handling that already guards `apply()`: a migrator whose plan throws yields a `failed` outcome carrying the reason, and `runPendingMigrations` returns instead of throwing.
- The run still stops at the failed migration — the rule that a failure must not be followed by more migrations on top of an unfinished one is unchanged.
- The boot path survives it: `ensureWorkspaceMigrated` resolves with the failed outcome instead of rejecting, so the host server goes on to start and to report `migration failed: <id> — <reason>` on stderr.
- A migration that fails to plan is not recorded in the journal, exactly like one that fails to apply: the next boot retries it.
