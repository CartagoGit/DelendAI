# f00809 — One generated format for pull request and issue text

## goal

Owner request (2026-11-04): pull request and issue text must have ONE defined format, generated by the product, identical whatever agent, LLM or host made the work. Today titles vary: "implement batch", "review batch", "review: 4 verdict(s) on d00418, x00989", conventional-commit titles with "(+3 more)", and issue titles from the error-reporting and issues plugins.

One template in packages/core, used by every path that opens or updates a change request (work publish, x01023 retitling, review packs from x01032 S4, the queue's close-approved batches) and by every issue opener (issues and error-reporting plugins).

Title: `<type>(<scope>): <summary> (<proposal-scope>)`. Type from the work kind (feat, fix, docs, perf, refactor, test, chore, review). Proposal-scope uses the branch grammar: x01003, x01003-S2, x01003-S1-S3, x01003-S1+S4, x01004+x01016. Summary from the proposal title or the slices shipped, under 72 characters.

Body, fixed sections in fixed order: What, Why (from the proposal), Slices shipped, Files and zones, Proof (step timings or "not proved locally"), Review notes. Reviews use the same template with Verdicts in place of Slices.

Issues: the same title rule; body with Summary, Where, Evidence, Expected and Actual, Proposal link.

Nothing an agent passes overrides the format: an agent may supply summary text, the template shapes it. Republish applies it through x01023's forge contract on GitHub and GitLab.

## why

Titles and bodies differ by agent and path, so history, review and triage cannot be read at a glance and cost tokens to decode. A single product-owned template is agnostic, bounded and cheap.
