# Publishing `@delendai/*` to npm — step-by-step guide

> Everything is **prepared** so you only need to run these steps with your account.
> Publishable packages (17): `@delendai/core`, `@delendai/client`,
> `@delendai/cli`, `@delendai/proposals`, `@delendai/rules`,
> `@delendai/memory`, `@delendai/git`, `@delendai/quality`,
> `@delendai/search`, `@delendai/notification`, `@delendai/docs`,
> `@delendai/deps`, `@delendai/audit`, `@delendai/logs`,
> `@delendai/status-marker`, `@delendai/test-convention`, and
> `@delendai/web-fetch`. All at `0.1.0`,
> `publishConfig.access=public`, `files` limited to `src` + README + LICENSE.

## 0. Requirements (once)
1. An npm account with access to the **`@cartago-git`** org (create it at npmjs.com →
   *Add Organization* → `cartago-git`, free for public packages).
2. Log in in the terminal:
   ```bash
   npm login            # or: bun pm whoami  /  npm whoami  to verify
   ```
3. (Recommended) 2FA in "Authorization and Publishing" mode → you will have to enter
   the OTP on every publish, or create an *Automation token* for CI.

## 0.0 Via CI (the user does nothing): push to `main`

With the `release.yml` and `pages.yml` workflows the cycle is **fully automatic
and driven by commits** — no need to bump versions by hand:

1. Merge/push to `main` with **Conventional Commits**
   (`feat:`/`fix:`/`perf:`/`feat!:`…).
2. The **Release** workflow runs `scripts/derive-version.ts`, which reads the commits
   since the last `vX.Y.Z` tag and decides the bump: `feat`→minor, `fix`/`perf`→patch,
   `!`/`BREAKING CHANGE`→major. Only `docs`/`chore`/`ci`/`test`/`style`/`build`/
   `refactor` → **does not publish**. A non-conventional commit with content → patch
   (safe default). If there is something to publish: validate + build +
   `bun run release --set=<derived version> --write --publish` (17 packages in
   order) + creates the **tag** `vX.Y.Z` + a **GitHub Release** with autogenerated notes.
   *Tag-driven:* the bump is NOT committed back to `main` (no CI loops).
3. The **Pages** workflow regenerates and deploys the site (docs web) from the
   live tool list (`--strict` mode: if a tool has no description, it fails).

**One-time setup:**
- Secret `NPM_TOKEN` (npm *Granular access token* with **Bypass 2FA** enabled) in
  *Settings → Secrets → Actions*. Since **November 2025** write tokens
  expire at 90 days as a legal maximum; the workflow
  [`.github/workflows/rotate-npm-token.yml`](../../.github/workflows/rotate-npm-token.yml)
  opens a reminder issue every ~3 months (see §0.1).
- *Settings → Pages → Source = "GitHub Actions"*.

If the commits since the last tag are all non-releasable (`docs`/`chore`/…),
the push to `main` does NOT publish. The sections below (§0/§1/§2) are the equivalent
manual path (`bun run release --bump=… --write --publish`), in case you want to force a release.

### 0.1 Granular token with Bypass 2FA (what is used today)
npm retired *Legacy* and *Automation* tokens in November 2025. The only token
type is **Granular**, and it is configured like this:
- Name: `delendai-release-ci`
- Packages/Scopes: `@cartago-git`
- Permissions: *Read and write*
- Organizations: *No access*
- Expiration: 90 days (legal maximum)
- **Bypass 2FA**: ✅ enabled ← key so CI does not ask for OTP

### 0.2 Automatic quarterly rotation
The [`rotate-npm-token.yml`](../../.github/workflows/rotate-npm-token.yml) workflow
runs on day 1 of every 3 months (`cron: "0 9 1 */3 *"`). If more than
75 days have passed since the last reminder, it opens an issue with the label
`npm-token-rotation` and the exact steps to regenerate the token. It can also
be launched manually from the *Actions* tab.

## 0. Assisted manual path: `bun run release`
A single command versions the 17 publishable packages **in lockstep** (all to the same
version, rewriting internal workspace dependencies to the real version) and
publishes in the correct order. By default it is **dry-run** (writes nothing):

```bash
bun run release                       # shows current versions + publish plan
bun run release --bump=patch          # plans a lockstep bump (dry-run)
bun run release --bump=minor --write  # applies the bump to each package.json
bun run release --set=0.2.0 --write   # sets an explicit lockstep version
bun run release --publish             # validates (bun run validate) + publishes in order
bun run release --bump=patch --write --publish   # full release in one pass
```
Flags: `--bump=patch|minor|major` · `--set=X.Y.Z` (mutually exclusive) · `--write`
(applies; default dry-run) · `--publish` · `--no-validate` · `--tool=bun|npm`
(default `bun`, which rewrites `workspace:*`). npm 2FA/OTP is entered
interactively for each package (inherited stdio).

The manual steps below (§1–§2) remain valid as a reference or if
you prefer to control each publish by hand.

## 1. Validate before publishing (from the repo root `/_projects/delendai`)
```bash
bun install
bun run validate            # typecheck + tests (must end green)
```

## 2. Publish (the command is the source of truth, NOT this guide)

The publish plan lives in `tools/scripts/release/release-plan.ts`
(`PUBLISH_ORDER`), and a spec (`release-plan.spec.ts`) derives it from the
presets + docs so it can never fall short. **Never enumerate the
packages by hand** — a previous version of this guide listed 17 of the
24 publishable ones and would have produced a broken partial publish.

```bash
# 1) See the plan (dry-run: versions + dependency order, no publishing)
bun run release

# 2) Publish in order (validate + build + publish ALL packages)
bun run release --publish                              # current versions
bun run release --bump=patch --write --publish          # or with lockstep bump
```

- The script publishes in dependency order (`core` → `client` → `cli` →
  plugins) and rewrites `peerDependencies` to resolved ranges with
  `--write`.
- `publishConfig.access=public` is already in each package; you do not need
  `--access public`.
- With 2FA, npm will ask for OTP per package; the recommended flow is the
  CI workflow (`release.yml`), which uses `NPM_TOKEN` with Bypass 2FA and
  OIDC provenance.
- The `"@delendai/core": "workspace:*"` entries live only in
  **devDependencies** (never published), so the `workspace:`
  protocol never reaches consumers.

## 3. Verify what was published
```bash
npm view @delendai/core version
bunx @delendai/cli --version
bunx @delendai/cli overview --json
bunx @delendai/cli --plugins=proposals,rules,memory,git,quality,search,notification,docs,deps validate
# Must print "ok": true and "assembles": true
```

## 4. Post-publish: migrate a consumer from local path to published package
Any consumer that was linking `delendai` via **local paths**
(tsconfig paths + vitest aliases pointing to `../../../delendai/...`)
must be moved to the real dependency when you publish:
1. In the consumer's `package.json` add real dependencies:
   ```jsonc
   "@delendai/core": "^0.1.0",
   "@delendai/proposals": "^0.1.0"
   ```
2. Remove the `paths` `@delendai/*` from the consumer's `tsconfig.base.json` and
   the `@delendai/*` aliases from its `vitest.config.ts` (so they resolve from
   `node_modules`).
3. `bun install` in the consumer and run its `bun test` (all green).
   - Note: packages publish **TS source**; vitest/bun transpile it. If a pure
     Node consumer fails, a `dist` build would have to be added (see §6).

## 5. Next versioning
- Bump version with `npm version patch|minor` in each package that changes (or use
  changesets if you want to automate it). Keep `delendai` and plugins compatible
  via `peerDependency` (`^0.x`).

## 6. (Optional, future) build to `dist` for pure Node consumers
Today we publish TS (bun-native, like `@delendai/keyer`). If you want to support
Node without transpilation: add a `tsc` build per package, `exports` pointing to
`dist/*.js` + `dist/*.d.ts`, and `files: ["dist"]`. Not needed for use with
Bun or via `bunx`.

---
*Summary: `bun install && bun run validate` → publish core → publish client/cli
→ publish plugins → `bunx @delendai/cli overview --json` to verify. That's all.*
