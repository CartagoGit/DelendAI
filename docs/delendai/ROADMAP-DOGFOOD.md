# The roadmap plugin: what delendai does with it, and what you replicate

delendai uses its own roadmap plugin on itself. This page separates the
two things that are easy to confuse: what is **the product** — yours as
soon as you load the plugin — and what is **delendai's own choice**, which
you replace with yours.

## What is the product

Nothing below depends on this repository. It is exercised, on projects
with other branch names and other layouts, by
`packages/core/tests/src/lib/e2e/roadmap-agnosticism.spec.ts`.

- **The authority file.** One file, tracked in git, that says what each
  target version promises. Markdown with a front-matter block, or plain
  YAML. Edited by hand or by `roadmap_plan_init` / `roadmap_plan_close`,
  and reviewed in a pull request like any other change.
- **The timeline.** Append-only, beside the file: when each entry was
  added or changed, by whom and why. It is derived — `roadmap_sync` says
  what it has not recorded.
- **The tools.** `roadmap_show`, `roadmap_sync`, `roadmap_readiness`,
  `roadmap_delta` and `roadmap_promotion` read; `roadmap_plan_init` and
  `roadmap_plan_close` write the two files and nothing else. None of
  them merges, pushes, bumps or tags.
- **The rules.** A gate nobody can look up answers `unknown`, never
  `fail`. A date never takes part in readiness. The bump reported is what
  the promises imply; the release tooling stays the authority.

## What you declare

Everything is optional. Declare no `file` and the plugin registers no
tool and says nothing.

```jsonc
// delendai.config.json
{
	"development": {
		"branches": { "integration": "trunk", "release": "release/2.x" }
	},
	"plugins": {
		"roadmap": {
			"options": {
				"file": "plan/ROADMAP.md",
				"versionFile": "package.json",
				"promotion": {
					"blockingGates": ["proposal-done", "path-exists"],
					"deferralPolicy": "block",
					"schedule": "0 6 * * 1"
				}
			}
		}
	}
}
```

| You declare | What follows from it |
| --- | --- |
| `development.branches` | The branches a promotion runs between. With one branch there is nothing to promote, and `roadmap_promotion` says so. |
| `options.file` | Where the authority lives. The timeline is beside it unless `timeline` names another place. |
| `options.versionFile` | A JSON file whose `version` says what is published. Without it `published` is `null`: nobody can say, which is not "no". |
| `promotion.blockingGates` | The gate kinds that hold a promotion. Every kind, when absent. |
| `promotion.deferralPolicy` | `block`: an open entry holds its version. `report`: it is listed as left to defer, and does not. |
| `promotion.schedule` | A cron expression, or `on-ready`. See below. |

## What delendai chose for itself

These are this repository's answers. Yours will differ, and nothing in
the plugin prefers ours.

| Choice | Here | Why it is ours and not a default |
| --- | --- | --- |
| The file | `docs/delendai/ROADMAP.md` | delendai keeps its project documents under `docs/delendai`. |
| The version file | `packages/core/package.json` | The core's version is the one releases are named after. |
| Blocking gates | `proposal-done` | Work here is tracked by proposals, so "delivered" means its proposal closed. |
| The projection | `apps/web/src/data/roadmaps.json`, regenerated by `gen:all` | The site is static and reads generated data; the drift gate fails when the copy lags. |
| The schedule | not declared | Opening release pull requests on a clock is the owner's decision; until it is taken, promotions are opened by hand. |

## Opening promotions on a cadence

A project that declares `promotion.schedule` and has a release branch
gets a workflow, generated from the configuration like the other forge
settings, that runs `open-promotion` when the cadence comes round. It
opens the pull request from the integration branch into the release
branch when three things hold, each read where it lives:

1. the checks the integration branch requires are green on its head;
2. code scanning reports no open alert on it (a project without code
   scanning has nothing to report, and is not held back by that);
3. the roadmap's blocking gates for the next unpublished version pass.

When any of them does not hold it opens nothing and says which. It never
merges: the release branch's own gate judges the pull request.

What you replicate is the configuration above. The workflow's own steps
— how the repository is checked out and its tooling installed — are this
repository's and are generated here by
`tools/scripts/governance/forge-settings.script.ts`; in another project
the same script, `open-promotion`, is run by whatever your forge runs.

## Keeping the projection honest

```bash
bun tools/scripts/gen/roadmap-projection.script.ts   # regenerate
bun tools/scripts/lint/roadmap-drift.script.ts       # compare
```

The roadmap file is the authority. When the JSON or the timeline lags
it, regenerate; never edit the projection.
