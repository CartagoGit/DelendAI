# `delendai://code-map` resource — d00010

> Track H of [q00006](docs/delendai/proposals/in-progress/plans/q00006-plan-hardening-post-auditoria-chatgpt-sol-cuarta-pasada.md).
> Adopters: any MCP host that wants a structural, repo-wide orientation in a single round-trip.

The `delendai://code-map` resource is the canonical "where do I look?"
answer for a coding agent that lands inside `@delendai/core`. A
client reads it **once** before issuing any deep navigation — the
contents enumerate every package, every plugin, every manifest
capability, and the top token hotspots in the repo.

> **b00239 rename:** the historical brand URI is still accepted as a
> deprecated alias (`code-map/resource.ts` mounts at whatever URI the
> caller passes, and emits a deprecation warning on stderr). New code
> MUST use `delendai://code-map`.

---

## Contract

| Field         | Value                                      |
| ------------- | ------------------------------------------ |
| **URI**       | `delendai://code-map` (overridable)        |
| **MIME type** | `application/json`                         |
| **Schema**    | `ICodeMap` (`CODE_MAP_SCHEMA_VERSION = 1`) |
| **Privacy**   | R1.1–R1.10 compliant (see below)           |

The resource is generated by
[`buildCodeMapResourceRegistration`](../../packages/core/src/lib/code-map/resource.ts)
and consumed via MCP's `resources/read` request. The schema is also
exposed via the public `@delendai/core` API:

````ts
import {
  buildCodeMapResourceRegistration,
  type ICodeMap,
  CODE_MAP_SCHEMA_VERSION,
} from '@delendai/core/public';

const reg = buildCodeMapResourceRegistration({ ttlMs: 60_000 });
// → `IResourceRegistration`; pass to `extraResources` of `IDelendaiHostConfig`.
````

## Schema

```ts
interface ICodeMap {
  schemaVersion: number;             // bump on breaking changes
  generatedAt: string;                // ISO timestamp
  packages: Array<{
    name: string;                     // npm name (e.g. `@delendai/core`)
    dir: string;                      // workspace-relative (e.g. `packages/core`)
    description: string;              // truncated to 200 chars
    agent: string | null;             // path of the AGENT.md or null
  }>;
  plugins: Array<{
    name: string;                     // npm name
    dir: string;                      // workspace-relative
    pluginId: string;                 // manifest id (kebab-case)
    summary: string;                  // one-liner from the manifest
    capabilities: readonly string[];  // tokens declared on the manifest
    agent: string | null;             // AGENT.md path or null
    tokenBudget: { warning: number; hard: number } | null;
  }>;
  hotspots: Array<{                  // top-32 by staticBytes
    kind: 'tool' | 'schema';
    id: string;                       // `<pluginId>.<tool-name>` or `<pkg>/<schema>`
    staticBytes: number;              // file size, byte estimate
  }>;
}
```

The map is intentionally narrow: no nested objects, no
`{ path, host, secrets }` leakage. See `generator.ts` for the
exact shape and the collector walks.

## Privacy guarantees (R1.1–R1.10)

`delendai://code-map` is the most data-rich resource the core ships.
It is also the most carefully gated against privacy leaks:

- **R1.1** Every `dir` field is **workspace-relative** (e.g.
  `plugins/proposals`, never `/home/.../plugins/proposals`).
- **R1.2** Only public npm names are surfaced in `name` (no
  `private: true` package of the host's own).
- **R1.3** No absolute paths, hostnames, environment variables,
  secrets, or user identifiers are ever written into the
  response.
- **R1.4** The resource is host-local: it is regenerated per
  workspace, so a multi-tenant host that boots against two
  repos gets two distinct code-maps.
- **R1.5** Tool ids inside `hotspots` follow the existing
  private/public separation — `staticBytes` is the BYTE SIZE of
  the file on disk, not any user data.
- **R1.6** `summary` and `description` come from `package.json`
  or `plugin.manifest.ts` — both are author-written text and
  must already obey the project's privacy policy before being
  shipped.
- **R1.7** Capabilities are tokens declared in the manifest's
  `capabilities: [...]` field — exactly the same public tokens
  exposed via `delendai://catalog/{compact,full}`.
- **R1.8** No personal data, no telemetry, no LLM-provider ids.
- **R1.9** The resource is a pure projection; there is no
  on-write trigger, no Redis, no remote call.
- **R1.10** A consumer that does not want the resource can
  simply omit it from `extraResources`; the core never falls
  back to a synthetic default.

## Use cases

1. **Boot-time orientation** — at the start of a multi-agent
   session, ask the host for `delendai://code-map`. The map tells
   every agent "which plugin owns what surface", so they can
   pick `proposals_branch_status` vs `git_branch_status` based
   on the user's stated intent instead of guesswork.

2. **Hotspot-aware routing** — token budgets vary widely across
   tools. The `hotspots[]` array lets a host prefer smaller
   tools when the user only wants a quick answer:

   ````ts
   const { hotspots } = JSON.parse(read('delendai://code-map').text);
   const smallest = hotspots.find((h) => h.kind === 'tool');
   // plan: call `smallest.id` first; only escalate to larger tools if it fails.
   ````

3. **Capability discovery** — `plugins[].capabilities` is the
   same vocabulary the proposals plugin uses to gate proposal
   composition. A host building an "audit" preset can read the
   map and pick the smallest subset of plugins needed:

   ````json
   "capabilities": ["audit", "multi-model", "self-improvement"]
   ````

   Then iterate `plugins[]` filtering by intersection.

4. **Plugin self-description** — a plugin that wants to advertise
   itself can write its `summary` and `capabilities` straight
   into `plugin.manifest.ts`; the generator picks them up
   automatically.

## Caching

`buildCodeMapResourceRegistration` accepts an optional `ttlMs`
that defaults to `0` (no caching — every `resources/read`
triggers a fresh `buildCodeMap()` call). Hosts that prefer
determinism can set `ttlMs: 60_000` and the resource will
serve the last snapshot until the TTL elapses; perfect for
environments where 50+ agents hammer the map in parallel.

The map's freshness is bounded by:
- `bun tools/scripts/gen/agent-md.script.ts` (regenerates the
  per-scope `AGENT.md` files that the map links to),
- `bun run gen:manifests` (refreshes `plugin.manifest.ts`),
- the host's own `bun` startup cycle.

The map does not auto-refresh; it is regenerated on the next
read after a TTL expiry.

## Tests

`packages/core/tests/src/lib/code-map/resource.spec.ts`:

- `buildCodeMap` returns a snapshot with the schema-version banner.
- Every entry uses a workspace-relative `dir` (no absolute paths leak).
- The four canonical packages are listed.
- Hotspots are sorted desc and clipped at 32.
- The resource registers a single handler under
  `delendai://code-map` (or a custom override).
- The handler's read returns the JSON projection.
- The custom-URI override is honoured.

`bun tools/scripts/check-agent-md.script.ts` keeps the per-scope
`AGENT.md` files referenced by the map in sync with the
generator.

## Drift

If you add a new plugin or package and forget to add an
`AGENT.md`, the `agent` field on the corresponding entry will
be `null`. Treat this as a hint to run
`bun tools/scripts/gen/agent-md.script.ts`.

If you add a new manifest capability, regenerate the catalog
via `bun run gen:manifests` so the `capabilities` field on the
resource matches.
