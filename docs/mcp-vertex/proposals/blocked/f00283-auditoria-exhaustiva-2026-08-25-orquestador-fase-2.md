### Hallazgos de Fase 1 relevantes para esta auditoría

Bugs reales, con evidencia archivo+línea, encontrados y corregidos durante la revisión empírica de las 59 propuestas (no simulados para esta auditoría):

1. **`tools/scripts/release/verify-published-manifest.script.ts:7-8`** (propuesta c00129) — importaba `FIRST_PARTY_PLUGIN_INDEX` y `GENERATED_FIRST_PARTY_MANIFEST_ENTRIES` por ruta interna (`../../../packages/core/src/lib/registry/...`) en vez de `@delendai/core/public`, violando `lint:cli-imports` (no-internal-core-imports). Además `GENERATED_FIRST_PARTY_MANIFEST_ENTRIES` ya está incluido dentro de `FIRST_PARTY_PLUGIN_INDEX.entries` (se hace spread en `first-party-index.ts:320`), así que el script duplicaba cada entrada generada. **Corregido**: import único desde `@delendai/core/public`, sin doble spread.
2. **`tools/scripts/lint/cli-ui-parity.map.json`** (propuesta f00170) — el comando CLI `adopt` (añadido en el mismo commit `c76050fe`) nunca se registró en el mapa de paridad CLI↔UI, rompiendo `lint:cli-ui-parity`. **Corregido**: waiver añadido siguiendo el patrón de `project`/`audit`.
3. **`packages/client/src/lib/transport/mcp-stdio-client.ts:72-82`** (propuesta x00228) — `textFromUnknown` construía `${value.name} ${value.message}` para cualquier `Error`, produciendo mensajes redundantes tipo `"Failed to call MCP tool "X": Error server offline"` (el literal `"Error"` no aporta información para el caso común). Esto rompió 4 tests de la extensión VSCode (`extensions/vscode/src/test/commands.spec.ts`) que esperaban el formato anterior — **regresión real, no solo test desactualizado**: el nuevo mensaje es objetivamente peor (duplica semántica). **Corregido**: solo se antepone el `name` cuando es distinto del genérico `"Error"`, con separador `:` consistente con la convención de stringify de errores; se añadieron 2 tests de regresión en `packages/client/tests/transport/mcp-stdio-client.spec.ts` que **no existían antes** — la lógica de clasificación de errores de transporte (`classifyTransportErrorKind`, `describeTransportError`) no tenía ningún test directo en `packages/client`, solo cobertura indirecta vía `.kind`.
4. **`docs/mcp-vertex/proposals/done/feats/f00087-...md`** — su `Files:` citaba `tools/scripts/create-plugin.ts`, renombrado a `tools/scripts/scaffold/create-plugin.script.ts` por r00015 sin rebaselinar `lint:proposal-files-exist`. **Corregido** con `--update` (mecanismo ya soportado por el propio lint, solo faltaba ejecutarlo).
5. **`tools/scripts/lint/proposal-cited-commits.baseline.json`** — `8199bd1d` (commit de un worktree `f00126-S3` nunca mergeado, documentado como superseded por `bbf3b945` en el propio `a00069`) apareció como "orphan commit" nuevo sin estar en el baseline. **Corregido** con `--update` (mecanismo también preexistente).
6. **Bug de concurrencia — colisión de ids de propuesta `x00231`–`x00235`** (ver Bug 2 abajo, sección de arquitectura del sistema de propuestas).

Estos 5+1 bugs comparten un patrón: **ninguno era detectable por las tools de "resumen agregado" (`state_health`, `quality_policy`, `proposal_diagnose`) que devuelven un "ok"**; los 5 primeros solo aparecieron al ejecutar `bun run validate` de verdad y leer su salida completa, y el sexto solo al comparar el contenido real de dos ficheros con el mismo id. Esto confirma un riesgo real señalado por el usuario durante la sesión: las tools de agregación de este proyecto son útiles para orientación rápida, pero **no sustituyen ejecutar el gate real**.

### Roadmap de mejora (priorizado)

### Inmediato (bajo riesgo, alto valor)
1. **Actualizar las 5 dependencias con CVE high** (`brace-expansion`, `fast-uri`, `ip-address`, `js-yaml`, `undici`) vía `bun update` + `lint:dependency-versions`; ninguna es breaking conocida a la versión fix.
2. **Exigir evidencia adjunta en `proposal_review action: approve`**: como mínimo, aceptar un `validateEvidence` (ya existe el parámetro en `proposal_transition`, pero no en `proposal_review`) o un hash de commit reciente + exit code, en vez de solo `note` de texto libre. Esto cierra directamente la brecha que el usuario señaló en la sesión.
3. **Hacer atómica la asignación de ids de propuesta** entre procesos concurrentes (lock de fichero o `O_EXCL` al reservar el siguiente id), para que dos agentes en el mismo repo nunca puedan generar el mismo id — el Bug 2 de esta auditoría es 100% reproducible con dos agentes activos y ocurrió sin que ninguno de los dos hiciera nada "raro".
4. **Que `proposal_review approve`/auto-transition borre explícitamente el fichero origen en la misma operación de escritura** (o falle atómicamente si no puede), en vez de depender de que el caller haga `git add -A` a tiempo antes de que otro proceso concurrente reescriba el árbol.

### Corto plazo
5. Añadir tests unitarios directos a los `builders` internos de `quality-policy.service.ts`, `project-health.service.ts`, `context-for-change` e `impact-analysis` (más allá del test de tool end-to-end).
6. Considerar **acotar el blast-radius de `lint:proposals` / `lint:cli-ui-parity`** a los ficheros tocados en el diff/branch actual en vez de a todo el árbol de propuestas del repo — así un agente trabajando en un tema no puede tumbar `validate` global por contenido de otro agente en otro tema (Bugs 3 y 4).
7. Documentar en el propio `plugin.manifest.ts`/README de `plugins/proposals` el comportamiento real de concurrencia esperado (single-writer asumido vs. multi-agente real) — el propio bootstrap ya exige `agent_worktree` por agente, pero nada en el código de `proposal_review`/`create_proposal` verifica ni advierte si ese aislamiento no se está usando.

### Medio plazo (eficiencia de tokens)
8. El catálogo (`agent-catalog.generated.json`) se regeneró **6 veces** en esta sesión solo para poder comitear cambios de propuestas no relacionados con el catálogo — cada regeneración cuesta una ejecución de script + un commit extra. Vale la pena evaluar si `catalog:check` puede excluir campos derivados de conteo de propuestas (que cambian con cada `create_proposal`/`transition` de cualquier agente) de su hash de "stale", para no forzar una regeneración en cascada por cada operación de propuestas de cualquier agente en el repo.
9. Unificar el patrón de "rebaseline con `--update`" (ya presente en `proposal-files-exist` y `proposal-cited-commits`) como convención documentada explícitamente en `AGENT-BOOTSTRAP.md`, para que un agente sepa buscarlo antes de intentar un fix manual — en esta sesión se descubrió por prueba y error leyendo el mensaje de error de cada script.

Solo vi **títulos de una línea**, nunca el análisis ni la evidencia de esos hallazgos, y no abrí ningún fichero de auditoría legacy deliberadamente hasta terminar la tabla de puntuación de arriba. Se documenta por transparencia; no se ha usado ese índice para sesgar ninguna puntuación.

Tras terminar mi propia auditoría, localicé y leí `docs/mcp-vertex/audits/legacy/2026-08-25-develop-external-audit-chatgpt-sol.md` (auditoría externa, "ChatGPT 5.6 Sol", segunda pasada, HEAD `e1b4cefd`, 3003 líneas, fuente directa del plan `q00004` que tengo fuera de alcance).
